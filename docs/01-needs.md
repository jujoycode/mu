# 01. 니즈 정의

## 방향 결정

세 가지 후보 중 **팀/개인 내부용 툴**로 확정.

- ~~내 제품에 내장할 엔진~~ → 아님
- ~~독립 CLI 개발자 도구~~ → 아님 (생태계·폴리시 부담 배제)
- ✅ 팀/개인 내부용 툴 → 반복 속도와 실사용 가치에 올인

내부용이므로: 바이너리 배포 불필요(git/npm이면 충분), 상표·도메인 부담 없음,
언어 선택 기준은 순수하게 "만드는 사람이 가장 빨리 달릴 수 있는가".

## 핵심 페인포인트 (기존 범용 에이전트 사용 시)

### 1. 내부 지식/스킬
- 팀 지식(런북, 컨벤션, 아키텍처 문서)이 개인 로컬에 흩어져 있고 배포·버전 관리가 안 됨
- 컨텍스트에 다 넣자니 부풀림, 안 넣자니 매번 재설명

### 2. SSH / 접속 정보
- 범용 툴엔 호스트 레지스트리·환경별 정책·감사 로그라는 개념 자체가 없음
- Claude Code도 bash로 ssh를 칠 수는 있지만, 어떤 호스트가 prod인지,
  뭘 확인받아야 하는지 모름
- 접속 정보/시크릿을 에이전트에게 어떻게 안전하게 다루게 할지 불안

## Build vs Fork

Pi는 MIT 오픈소스라 포크 후 확장도 가능한 선택지였다.
그러나 **바닥부터 직접 구현**으로 결정:

- 코어 루프는 몇백 줄 수준이라 구현 부담이 작음
- 학습 + 완전한 통제가 내부 툴의 부가 가치
- 단, Pi 소스는 아키텍처 레퍼런스로 계속 참고 (같은 TS라 코드 레벨 참고 가능)

## 성공 지표

- **주간 실사용 인원** (도그푸딩 → 팀 확산)
- **mu로 완수한 태스크 수**

## 실패 시나리오 — 항상 경계할 것

1. **"그냥 Claude Code가 더 좋은데?"** — 내부 툴 최대 사망 원인.
   범용 코딩 능력으로 경쟁하면 반드시 진다. 범용 툴이 접근 못 하는
   내부 컨텍스트·시스템(스킬, SSH)에만 가치를 걸어야 산다.
2. **제작자 흥미 소진** — 두 번째 사망 원인.
   판단 기준: "3주 뒤에도 계속 만지고 싶은가?" 이 기준이 언어 선택에도 반영됨.
